# Scalability Harness — Reference

`@midgard-manager/scalability-harness` is a standalone benchmark package at
`demo/midgard-manager/packages/scalability-harness/`. It drives load against a
running Midgard node, collects Prometheus/Loki/Tempo evidence, analyses tier
results, and produces per-run and per-plan Markdown reports.

## Source layout

```
src/
  bin/index.ts              — CLI entry point (run, preflight, tiers commands)
  config/
    scenario.ts             — ScalabilityScenario interface and validateScenario()
    plan.ts                 — PlanConfig interface and validatePlan()
    tiers.ts                — generateTiers() ramp logic
  runner/
    load-runner.ts          — LoadRunner: per-tier HTTP load driver
    scenario-runner.ts      — runScenario(): tier loop, evidence capture, report write
    preflight.ts            — runExecutionReadinessPreflight()
    node-probe.ts           — node health probing
    tx-generator.ts         — transaction generation
    host-resources.ts       — load-driver CPU/memory sampling
  evidence/
    artifacts.ts            — ArtifactWriter: per-run directory management
    plan-artifacts.ts       — PlanArtifactWriter: plan directory management
    load-events.ts          — per-request JSONL event types
    loki.ts                 — Loki log evidence capture
    tempo.ts                — Tempo trace evidence capture
  analysis/
    analyzer.ts             — BenchmarkConclusion, runClassificationPolicy
    tier-summary.ts         — AnalysisTierSummary derivation from TierSummary
    collapse.ts             — collapse detection logic
    accepted-to-committed-latency.ts — cohort-alignment latency estimation
  metrics/
    prometheus.ts           — Prometheus snapshot client
  report/
    markdown.ts             — per-scenario Markdown report renderer
    plan-markdown.ts        — plan-level report renderer (renderPlanReport, buildPlanConclusion)
scenarios/                  — 12 scenario JSON files (one per benchmark tier)
plans/                      — plan JSON files (ordered scenario sequences)
tests/
  unit/                     — Vitest unit tests
```

## Scenarios

Each file in `scenarios/` configures a single benchmark run. Scenario files are
referenced by plan files and can also be run directly with `--scenario`.

| File                               | runId                         | Target TPS | Test plan section              |
| ---------------------------------- | ----------------------------- | ---------- | ------------------------------ |
| `warmup.json`                      | `warmup`                      | 100        | §8.1 warm-up                   |
| `initial-800.json`                 | `initial-800`                 | 800        | §8.1 initial TPS validation    |
| `institutional-1000.json`          | `institutional-1000`          | 1,000      | §8.1 institutional baseline    |
| `institutional-5000.json`          | `institutional-5000`          | 5,000      | §8.1 institutional load        |
| `stress-10000.json`                | `stress-10000`                | 10,000     | §8.1 institutional stress      |
| `practical-24985.json`             | `practical-24985`             | 24,985     | §8.1 practical estimate target |
| `spike.json`                       | `spike`                       | 49,970     | §8.1 peak spike                |
| `baseline-100-800.json`            | `baseline-100-800`            | 800        | §13 step-ramp baseline         |
| `baseline-100-800-replay.json`     | `baseline-100-800-replay`     | 800        | §13 replay variant             |
| `saturation-discovery.json`        | `saturation-discovery`        | 1,600      | §8.3 saturation discovery      |
| `saturation-discovery-replay.json` | `saturation-discovery-replay` | 1,600      | §8.3 replay variant            |
| `saturation-ramp-25pct.json`       | `saturation-ramp-25pct`       | varies     | §8.3 25% increment ramp        |

### Key scenario fields

```jsonc
{
  "runId": "warmup",
  "description": "...",          // free-text, appears in the run manifest and report header
  "nodeEndpoint": "http://localhost:3000",
  "prometheusEndpoint": "http://localhost:9090",
  "lokiEndpoint": "http://localhost:3100",   // optional — enables Loki log capture
  "tempoEndpoint": "http://localhost:3200",  // optional — enables Tempo trace capture
  "outputDir": "benchmark-runs",
  "seed": "warmup-2026-05-18",
  "l1ProviderMode": "emulator",  // kupmios | blockfrost | emulator | unknown
  "walletMode": "test-wallet",   // test-wallet | external-key
  "transactionType": "one-to-one",
  "startTps": 100,
  "maxTps": 100,
  "stepMultiplier": 2,           // or use ramp: { strategy, percentIncrement }
  "tierDurationSeconds": 600,
  "recoverySeconds": 120,
  "batchSize": 50,
  "concurrency": 4,
  "retryAttempts": 3,
  "retryDelayMs": 500,
  "stopConditions": { ... },
  "runClassificationPolicy": { ... }  // optional acceptance criteria overrides
}
```

Tiers are generated by `generateTiers()`: starting from `startTps`, each tier
multiplies by `stepMultiplier` (or increments by `percentIncrement`) until
`maxTps` is reached. When `startTps === maxTps` the scenario has a single tier.

## Plans

A plan encodes an ordered sequence of scenarios. Plans are stored in `plans/`.

### `plans/standard-progression.json`

Full §8.1 benchmark sequence. Runs scenarios in order and stops on the first
`Failed` or `Blocked` result.

```
warmup → initial-800 → institutional-1000 → institutional-5000 → stress-10000 → practical-24985
```

### `plans/saturation.json`

Post-formal-tier saturation sequence (§8.3). Runs both scenarios regardless of
individual results (`stopOnFailure: false`).

```
saturation-discovery → saturation-ramp-25pct
```

### Plan file format

```jsonc
{
  "planId": "standard-progression",
  "description": "...",
  "outputDir": "benchmark-plans", // directory for all plan output
  "stopOnFailure": true, // default true; set false for saturation exploration
  "scenarios": [
    "../scenarios/warmup.json", // paths relative to the plan file
    "../scenarios/initial-800.json",
  ],
}
```

**Stop condition:** the harness stops after a scenario returns `Failed` or
`Blocked` when `stopOnFailure` is true. Scenarios that return `Passed with
Observations` do not trigger a stop. Remaining scenarios are recorded as
`Skipped`.

## CLI

Build before first use:

```sh
cd demo/midgard-manager/packages/scalability-harness
pnpm build
```

### `run --plan`

Run a full plan:

```sh
node dist/bin/index.js run --plan plans/standard-progression.json
node dist/bin/index.js run --plan plans/saturation.json
```

Dry run — validates all scenario files and prints the tier breakdown without
creating any load:

```sh
node dist/bin/index.js run --plan plans/standard-progression.json --dry-run
```

Override the output directory:

```sh
node dist/bin/index.js run --plan plans/standard-progression.json --output-dir /tmp/bench
```

### `run --scenario`

Run a single scenario:

```sh
node dist/bin/index.js run --scenario scenarios/warmup.json
node dist/bin/index.js run --scenario scenarios/initial-800.json --dry-run
node dist/bin/index.js run --scenario scenarios/stress-10000.json --max-tier 2
node dist/bin/index.js run --scenario scenarios/warmup.json --run-id warmup-v2 --output-dir /tmp/runs
```

`--scenario` and `--plan` are mutually exclusive.

Scenario-mode-only flags: `--run-id`, `--max-tier`, `--no-increase`.

### `preflight`

Run execution readiness checks before a formal run:

```sh
node dist/bin/index.js preflight --scenario scenarios/warmup.json
```

The plan mode runs preflight automatically against the first scenario's
endpoints before any load starts.

### `tiers`

Print the tier breakdown for a scenario without running anything:

```sh
node dist/bin/index.js tiers --scenario scenarios/practical-24985.json
node dist/bin/index.js tiers --scenario scenarios/saturation-ramp-25pct.json --max-tier 4
```

### Common flags

| Flag                      | Applies to                | Description                                            |
| ------------------------- | ------------------------- | ------------------------------------------------------ |
| `--dry-run`               | `run`                     | Validate config and print tier breakdown; no load      |
| `--output-dir <dir>`      | `run`                     | Override the scenario/plan `outputDir`                 |
| `--request-events <mode>` | `run`                     | `off` \| `sampled` \| `all` (per-request JSONL events) |
| `--run-id <id>`           | `run --scenario`          | Override the scenario's `runId`                        |
| `--max-tier <n>`          | `run --scenario`, `tiers` | Stop after tier index n (inclusive)                    |
| `--no-increase`           | `run --scenario`, `tiers` | Run only the first tier                                |

## Artifact structure

### Single scenario run

```
benchmark-runs/
  2026-05-18T14-00-00.000Z-warmup/
    scenario.json           — scenario config as loaded
    run-manifest.json       — runId, git SHA, host info, endpoints
    load-events.jsonl       — per-request events (if --request-events != off)
    tier-summaries.jsonl    — one JSON line per tier
    prometheus-samples.json — all Prometheus counter/gauge snapshots
    loki-captures.json      — Loki log captures (if lokiEndpoint configured)
    tempo-captures.json     — Tempo trace captures (if tempoEndpoint configured)
    summary.json            — machine-readable BenchmarkConclusion
    report.md               — human-readable scenario report
    stdout.log / stderr.log
```

### Plan run

```
benchmark-plans/
  2026-05-18T14-00-00.000Z-standard-progression/
    plan-manifest.json      — plan metadata and host info
    plan-summary.json       — machine-readable PlanConclusion + scenario index
    plan-report.md          — aggregated human-readable plan report
    01-warmup/              — per-scenario subdirectory (1-based, zero-padded)
      scenario.json
      run-manifest.json
      tier-summaries.jsonl
      prometheus-samples.json
      summary.json
      report.md
      ...
    02-initial-800/
      ...
    03-institutional-1000/
      ...
```

Scenario subdirectories are named `<NN>-<runId>` (e.g., `01-warmup`,
`02-initial-800`) so they sort in execution order without timestamps.

## Report format

### Per-scenario `report.md`

Sections:

- **Run Metadata** — runId, git SHA, host, endpoints, tier configuration
- **Throughput Progression** — observed enqueued/accepted/committed TPS per tier
- **Transaction Totals** — aggregate deltas across all tiers
- **Peak Metrics** — peak queue size, peak mempool size, commitment and merge failures
- **Inclusion Latency (p95)** — cohort-alignment estimate of accepted-to-committed latency
- **Collapse Analysis** — first collapsed tier, primary bottleneck, contributing factors
- **Final Disposition** — classification, highest completed TPS, collapsed TPS, notes

### Plan-level `plan-report.md`

Sections:

- **Plan Metadata** — planId, git SHA, host, started at, scenario count
- **Execution Overview** — table of all scenarios: result, tiers passed, highest TPS, collapse TPS, bottleneck
- **Throughput Progression** — average observed TPS per scenario
- **Transaction Totals** — aggregate counts across all executed scenarios
- **Peak Metrics per Scenario** — queue/mempool peaks and failure counts per scenario
- **Inclusion Latency (p95) per Scenario** — p50/p95/p99 per scenario
- **Collapse Analysis** — per-scenario collapse details where detected
- **Final Disposition** — overall plan classification with highest-passed scenario and stop reason
- **Artifact Index** — paths to all per-scenario subdirectories

### Classifications

Per-scenario (`BenchmarkConclusion.classification`):

| Classification             | Meaning                                                     |
| -------------------------- | ----------------------------------------------------------- |
| `Passed`                   | All tiers completed within acceptance criteria              |
| `Passed with Observations` | All tiers completed; non-blocking policy violations         |
| `Failed`                   | One or more tiers collapsed or acceptance criteria violated |
| `Blocked`                  | Harness error or preflight failure prevented the run        |

Plan (`PlanConclusion.classification`):

| Classification             | Meaning                                              |
| -------------------------- | ---------------------------------------------------- |
| `Passed`                   | All scenarios passed                                 |
| `Passed with Observations` | All scenarios completed; some had observations       |
| `Failed`                   | One or more scenarios failed; remaining were skipped |
| `Blocked`                  | Harness error before any scenario could complete     |
